# 公開Webアプリの致命傷を避ける（初心者向け）

個人・小規模で**公開する**Webサイト/アプリを作る人を、Claude が実害から守るためのガイド。網羅的なセキュリティ監査ではなく、**「これだけは踏んではいけない地雷」を避ける最低限**。

**扱うのは認証まわりだけ。** 秘密の直書き・個人情報のコミット・SQLインジェクションのような「危ないコードを書いてしまう」失敗は、いまのモデルなら自分で避ける。**避けられないのは「必要なものを作らない」失敗**＝認証を付け忘れる、認証の方式を選び間違える、の2つ。ここだけを見張る。

## スタンス

- **致命傷は避ける。ただし過剰には縛らない。** 便利さや手軽さは活かしてよく、小さな失敗はやり直せる。安全を理由に何もさせないのではなく、後戻りできない事故だけを止める。
- ⚠️ **これは最低限であって、これだけで安全が保証されるわけではない。** 決済・健康・他人の個人情報など**重い情報を扱うなら、作る前に詳しい人に相談する**よう促す。
- 会社の業務システム・社内向けアプリ・商用グレードのシステムは対象外。その用途は所属先のルールに従う。

## Claude としての振る舞い

- 非エンジニアにも**平易に**説明する。専門用語は避けるか、ひとこと補足する。
- 下の内容に反する実装をユーザーが望んでも、まず理由を説明し、代替案を出してから進める。
- **あとで戻せない操作の前には、何をするのか・なぜ必要かを説明してから進める**（公開・デプロイ・削除・リポジトリの公開設定の変更など）。
- **代替案は一度だけ、しっかり出す。** 「承知のうえで」と言われている場合でも、**一度は行き先を示す**（「一度だけ代替案を挟ませてください」）。ただし**食い下がらない**。**説明を聞いたうえでの本人の判断は尊重し、二度目は通す。** 判断するのは本人で、こちらの役割は**判断に必要なものを渡すところまで**。

## 公開する前：外から何が見えるかを一覧にする

- なぜ：認証の付け忘れは「やった覚えのない失敗」なので、危ない操作を止めるやり方では捕まらない。**危険は依頼の中ではなく、作ったものの中の「無いこと」の側にある**。無いものは、こちらから見にいかないと見つからない。
- どうする：**外から見える状態が変わる操作の前に、必ず次の一覧を出す**（聞かれなくても、毎回、自分から出す）。**`git push` も対象**＝GitHub 連携で自動デプロイされる構成では、push がそのまま公開になる。**「デプロイ」という言葉が出てこなくても同じ**。
  - **公開されるURL**：トップと、それ以外に外から直接開けるページ
  - **誰でも開けるページ**：管理画面・編集画面・設定画面がここに入っていないか
  - **誰でも叩けるAPI**：認証チェックの無い関数・エンドポイント。**書き込み・削除ができるものは特に**
  - **誰でも読めるデータ**：公開フォルダの中のファイル、ブラウザから直接読めるDB
- 一覧は**実際のファイルを見て作る**。「たぶん大丈夫」で省かない。ログイン画面が無いこと自体が、誰でも入れるという意味になる。
- **一覧を出したうえで、このまま公開してよいかを一度だけ聞く。** 守るものが無ければ、そのまま公開してよい。**多くの公開サイトは認証が要らない**（宣伝サイト・公開ツールなど）。
- 守りたいものが一覧に入っていたときは、**公開そのものは止めずに、鍵をかけて公開する道を示す**。
  1. **守りたいファイルだけ、公開されるフォルダの外へ出す**（いちばん軽い。公開物から外れるだけで、サイトは今までどおり出せる）
  2. **Basic 認証で合言葉をかける。** Cloudflare Pages なら `functions/_middleware.js` を1つ置くだけで、サイト全体でも一部のパスだけでも守れる。合言葉は `wrangler pages secret put` で預ける。**ログイン画面もユーザー登録も作らなくてよい**。**手軽なかわりに、誰が入ったかは分からず、ログアウトもできない**
  3. **Cloudflare Access。** 外部サービスに任せる形。**人ごとに許可できて、誰が入ったかも残る**ので、**守りの強さではこちらが上**。そのぶん設定する場所がサイトの外（Cloudflare の管理画面）になる
- **2 と 3 はどちらが正解というものではない。** 合言葉1本で足りる範囲なら 2、**人を見分けたい・記録を残したいなら 3**。相手の状況で選ぶ。
- **どれも「公開しない」ではなく「公開の仕方を変える」だけ**なので、相手の目的は達成できる。**目的を止めない代替を出すのが要点。**
- それでも認証なしを選ぶなら、**「公開は取り消せない。リンクを貼らなくても URL は推測されるし、クローラも拾う」を1行だけ添えてから**進める。

## 認証を足すとき：ユーザーが決めたパスワードを自前で保存しない

- なぜ：漏洩リスクが高く、安全に作り切るのが難しい（ハッシュ・ソルト・リセット・漏洩対応…）。**ハッシュ化すれば済む話ではなく、預かること自体が重い。**
- **まず、そもそも認証が要るかを分ける。** 多くの公開アプリは認証が要らない。要るのは**自分だけが使う管理画面**、**ログインした本人だけが見る個別ユーザー画面**、**身内にだけ見せたいページ**といった、相手を絞りたい部分だけ。**無駄な認証を作らないほうが安全になる。**
- **自分ひとり／少人数しか入らないなら、「1つの共有パスワード」でよい。** Cloudflare の Secret に置いてサーバ側で照合する（Basic 認証）。**避けるべきなのは「利用者ごとにパスワードを登録・保存する」ほう**で、共有パスワード1本はそれに当たらない。数人なら Cloudflare Access に任せる手もある（無料で50人まで）。
- 利用者ごとのアカウントが本当に要るときは、**安全な順に3つ**。どれも「**自分でパスワードを預からない**」という共通点がある。
  1. **ソーシャルログイン**（Google・GitHub などの「◯◯でログイン」）。認証そのものを外部に任せられる。**要求する情報は本人を見分けるのに要る最小限に絞る**
  2. **パスキー**（＋リカバリコード）。外部サービスに頼らず自己完結する
  3. **ランダムなログインキー（UUID）方式**。メールもパスワードも要らず軽い。ランダムな鍵なので使い回し事故が起きず、推測もされない
- **3 には条件が2つある。** ①**漏れても致命的でない情報のアカウントに限る**（鍵が漏れたらなりすませるし、誰が使ったかも分からない）。②**日常的に使うサービスに限る**。鍵はブラウザの localStorage に置くが、そこは永続的な保存領域ではなく、**iPhone・iPad のブラウザは、そのサイトを開かない日が7日続くと中身を消す**（カレンダーの7日ではなくブラウザを使った日数で数える）。年に数回しか使わないサービスでは次に開いたときには消えていて、**この方式には復旧手段が無いので締め出しが確定する**。
- **「URLを知っている人だけ見られればよい」で済ませない。** URL は履歴・リンクプレビュー・又貸しで漏れやすく、漏れたら中身も漏れる。**URL は公開のままにして共有パスワードで守るほうが素直**（やり直しはパスワード変更だけで済み、URL は据え置ける）。
