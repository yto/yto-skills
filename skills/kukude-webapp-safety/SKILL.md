# 公開Webアプリの致命傷を避ける（初心者向け）

個人・小規模で**公開する**Webサイト/アプリを作る人を、Claude が実害から守るためのガイド。網羅的なセキュリティ監査ではなく、**「これだけは踏んではいけない地雷」を避ける最低限**。

## スタンス

- **致命傷は避ける。ただし過剰には縛らない。** 便利さや手軽さは活かしてよく、小さな失敗はやり直せる。安全を理由に何もさせないのではなく、後戻りできない事故だけを止める。
- **致命傷 = 取り返しがつかない/被害が大きいもの**：秘密（APIキー・トークン・パスワード）の漏洩、個人情報の流出、他人による不正利用・課金事故。
- ⚠️ **これは最低限であって、これだけで安全が保証されるわけではない。** 決済・健康・他人の個人情報など**重い情報を扱うなら、作る前に詳しい人に相談する**よう促す。

## Claude としての振る舞い

- 危険になりうる操作（秘密をコードに書く、リポを Public にする、認証を自前で作る等）の**前にリスクを先に指摘**し、安全な代替を提案する。
- 非エンジニアにも**平易に**説明する。専門用語は避けるか、ひとこと補足する。
- 下の原則に反する実装をユーザーが望んでも、まず理由を説明し、代替案を出してから進める。
- **あとで戻せない操作の前には、何をするのか・なぜ必要かを説明してから進める**（公開・デプロイ・削除・リポジトリの公開設定の変更など）。

## 避けるべき致命傷（原則）

1. **秘密のキー・トークンをソースコードに直書きしない。**
   - なぜ：漏れると不正利用・課金事故に直結する。Public リポなら即バレる。一度コミットすると Git 履歴に残り、消すのは難しい。
   - どうする：秘密は**サーバ側の環境変数/Secrets** に置く（例：Cloudflare の Secrets、`.env` は `.gitignore`）。フロントのJSに秘密を置かない（ブラウザに送ったものは誰でも見られる）。

2. **個人情報は、そもそも取らない。取ったものはリポジトリにコミットしない。**
   - なぜ：**持たなければ漏らしようがない**。個人情報を持つほど、漏れたときの被害も、法律上の責任も重くなる。リポジトリは Public なら即流出、Private でも履歴に残る。メールアドレス・氏名・電話番号・顧客名簿など。
   - どうする：**使う当てが無いなら集めない、必要になってから足す**。名前や連絡先を入力させる前に「それは本当に要るか」を一度確認する。取ると決めたものはコード/リポに入れず、必要ならDBに。テストデータにも実在の個人情報を使わない。

3. **ログインの合否をブラウザ側（JavaScript）だけで判定しない。**
   - なぜ：ブラウザに送ったコードやデータは誰でも書き換え・閲覧できる。JSの`if`で「ログイン成功」にしても素通りされる。
   - どうする：**認証・認可の判定は必ずサーバ側**（API/Functions）で行う。フロントの制御は見た目だけと考える。

4. **リポジトリは基本 Private にする。**
   - なぜ：書きかけのコードや、うっかり入れた秘密・個人情報の被害を限定できる。
   - どうする：既定は Private。**GitHub Pages で公開する等、仕組み上 Public が必須のときだけ** Public にし、そのリポには秘密・個人情報を絶対に入れない。**Public に切り替える前には、秘密や個人情報が混ざっていないかを必ず確認する**（履歴に残ると後から消すのは難しい）。

5. **ユーザーが決めたパスワードを自前で保存する認証は避ける。**
   - なぜ：漏洩リスクが高く、安全に作り切るのは難しい（ハッシュ・ソルト・リセット・漏洩対応…）。
   - どうする：**認証は外部に任せられるならそれが一番安全**。第一候補は**ソーシャルログイン**（Google・GitHub などの「◯◯でログイン」）で、パスワードもパスキーも自分で扱わずに済む。ただし**要求する情報（スコープ）は本人を見分けるのに要る最小限に絞る**（メールアドレスやプロフィールまで取らない）。次が**パスキー**（＋リカバリコード）、それも難しければ**ランダムなログインキー（UUID）方式**（メール不要・パスワード不要）。ランダムな鍵なので、他のサービスと同じパスワードを使い回す事故が起きず、推測もされない。
   - ログインキー方式には条件が2つある。**①漏れても致命的でない情報のアカウントに限る**（鍵が漏れたらなりすませるし、誰が使ったかも分からない）。**②日常的に使うサービスに限る**。鍵はブラウザの localStorage に置くが、そこは永続的な保存領域ではなく、iPhone・iPad のブラウザは7日ほど開かないと中身を消す。**年に数回しか使わないサービスでは次に開いたときには消えていて、この方式には復旧手段が無いので締め出しが確定する**。年数回のサービスなら、本人確認の媒体をアプリの外に持つ方式（ソーシャルログインなど）にする。
   - **例外**：管理画面などを守る「1つの共有パスワード」は使ってよい。**Cloudflare の Secret（環境変数）に置き、サーバ側で照合する**なら、管理者ひとり／少人数で使う範囲では妥当な選択。避けるべきなのは「利用者ごとにパスワードを登録・保存する」ほうで、共有パスワード1本はそれに当たらない。

6. **守るべきデータがあるのに、認証なしで公開しない。**
   - なぜ：本人だけが見るべき情報（個別ユーザーのデータ、非公開の記録など）を、誰でも読める状態で公開すると流出になる。
   - どうする：下の切り分けで「守りたいデータがあるか」を先に判断し、あるなら公開前に必ず認証をかける。

## 構成は最小から始める（作り込まない）

- やりたいことに対して、**一番シンプルで安全な構成**を選ぶ。文章・画像を見せるだけなら静的サイト（HTMLなど）で十分。データの保存やログインが要るならDBを検討する。
- **まず最小構成で動かし、必要になってから増やす**（最初から作り込まない）。作り込みすぎるほど、扱う秘密・認証・個人情報が増えて地雷も増える。
- 複雑な構成を選ぶときは、なぜ必要かを平易な言葉で説明してから進める。

## 認証は「そもそも要るか」を先に分ける

作り始める前に切り分ける。無駄な認証は作らない＝作り込みの地雷を減らす。

- **多くの公開アプリは認証不要**（誰でも見られる/使えるほうがよい宣伝サイト・公開ツールなど）。
- 認証が要るのは、**自分だけが使う管理画面**、**ログインした本人だけが見る個別ユーザー画面**、**身内にだけ見せたいページ**（イベント参加者向け・家族向けなど）といった、相手を絞りたい部分だけ。
- **「公開してよいもの」と「本人だけが見るべきもの」が混ざるときは、その境目を確認してから作る**（原則6に直結）。
- 認証が必要になったら、上の原則5の順（**ソーシャルログイン → パスキー → UUIDキー**）で検討する。**自分だけ／数人だけの管理画面**や**身内向けのページ**なら、共有パスワード1本をサーバ側で照合する方式（原則5の例外）や、プラットフォームの認証に任せる手もある（例：Cloudflare Access は無料で50人まで）。**むしろそのほうが軽い。**
- 「**URLを知っている人だけ見られればよい**」で済ませたくなる場面でも、URL は履歴・リンクプレビュー・又貸しで漏れやすく、漏れたら中身も漏れる。**URL は公開のままにして共有パスワードで守るほうが素直**（やり直しはパスワード変更だけで済み、URL は据え置ける）。

## 使わない範囲（このスキルの対象外）

会社の業務システム・社内向けアプリ・商用グレードのシステムは対象外。その用途は、所属先のルールや情報システム部門・セキュリティの専門家の方針に従う。ここで扱うのは**個人・小規模で公開する**場面に限る。
